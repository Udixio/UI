### M3-L02 — Valeur « avant » = dernière géométrie stable, bornée à la racine [fusionne : M2-L01, M4-L01]
- Énoncé : pour chaque élément d'une racine suivie, le runtime garde le rect lu en phase lecture de la frame précédente, après écritures. C'est la valeur « avant » du FLIP, sans aucune lecture dans le callback de mutation. Invalidée par un ResizeObserver sur la racine (changement de taille sans mutation : `md:`, container query) et par tout MutationObserver `childList` ou attribut de la racine. Le même cache sert au départ d'un nœud déjà retiré (L10) et au réordonnancement (L05).
- Familles : F7, F8, F10, F19
- Nature : global (cache et observateurs) ; instance (portée)
- Variante M4-L01 (points de capture par environnement) : « le runtime garde la dernière géométrie stable de chaque élément `data-motion="layout"` (relevée après le commit précédent, tenue à jour par `ResizeObserver` et au défilement) et s'en sert comme « avant » dès qu'un changement observable est détecté. Points de capture : React = valeur stockée dans le `useLayoutEffect` du commit précédent (correction de M4) ; Svelte = `$effect.pre`, qui tourne avant la mise à jour DOM du composant ; Angular = lecture dans le gestionnaire d'événement avant l'écriture du signal, puis `afterRenderEffect` pour mémoriser « après » ; HTML = lecture dans le gestionnaire d'entrée avant `setAttribute`. » Familles : F7, F8, F13. Nature : instance.
- Variante M2-L01 (mesure mémorisée) : « chaque instance `layout` garde la géométrie lue en fin de cycle (phase lecture, M1-04) ; au changement détecté, « avant » = cette mémoire, relue seulement si invalidée (scroll, resize, ResizeObserver). Lecture réelle avant mutation là où elle existe : React `getSnapshotBeforeUpdate` (nœud classe interne), Svelte `$effect.pre`, Angular `effect()` de composant (à confirmer par spike), HTML pur via `motion.capture(el)` au point de mutation. » Familles : F7, F8, F10. Nature : instance.
- Avantages : une seule source de vérité pour tous les environnements ; lecture groupée dans la frame unique (§8.0 #3) ; aucun point pré-mutation requis. [M1] source de vérité unique pour les quatre environnements, lecture groupée dans la frame unique. [M2] une source de vérité pour tous les environnements, lecture groupée en frame unique. [M4] une seule source de vérité, lecture groupée en frame (§8.0 #3), base de tout le FLIP. [M5] un seul cache pour L03, L05, L08 et L10.
- Limites : valeur périmée si un changement non observé déplace un élément hors racine ; une lecture de layout par frame et par élément suivi (coût à mesurer) ; toutes les lectures précèdent les écritures de la frame. [M1] valeur périmée si un élément sort de la racine sans mutation observée. [M2] coût de lecture par élément suivi. [M4] valeur périmée si le mouvement n'est pas observé. [M5] coût à mesurer avant de figer le budget.
- Conflits : M1-L02, M2-L01, M4-L01 (union des annotations).
- Cohérence : réutilise la frame unique et ses phases lecture / écriture (§8.0 #3) ; l'écriture qui suit une invalidation ResizeObserver est différée à la frame suivante (pas de boucle) ; aucun verbe ni option nouvelle · jugements : ok 4 · exception 0
- Verdicts : valide 4 (M1, M2, M4, M5) · neutre 0 · conteste 0

### M1-L01 — Transaction de layout : géométrie lue avant mutation, une passe de lecture [fusionne : M5-L01, M1-L02, M3-L03 (variante contestée)]
- Énoncé : tout changement de layout passe par `motion.layout(portée, mutation)` ; la portée est lue en une seule passe de lecture (First), la mutation s'exécute synchrone, une seule passe de lecture (Last), puis les inversions (`transform`) sont écrites dans la frame unique (§8.0, M1-04).
- Familles : F7, F8, F10
- Nature : instance (la portée) ; le registre de géométrie reste global
- Variante M5-L01 (surface `mutate`) : « `layout` ne s'applique qu'à un état observable (classe, `data-*`, contenu). Le noyau expose `mutate(el, fn)` comme point pré-mutation ; les adaptateurs reçoivent l'état surveillé en argument. » ; forme HTML, React, Angular, Svelte et noyau telle que publiée dans M5-L01 ; `defineMotion('nav-indicator', { verb: 'layout' })`. Familles : F7, F8. Nature : instance.
- Variante M1-L02 (points de capture par framework) : « First est pris au point le plus proche de la mutation : Svelte `$effect.pre` ; Angular `afterRender` en phase `EarlyRead` (à vérifier) ; React, sans point pré-mutation hors classe : capture dans le gestionnaire d'événement déclencheur, avant `setState`, ou store alimenté par le dernier `useLayoutEffect` ; HTML pur : L01 ; le store sert de repli. » Familles : F7, F8, F3. Nature : les deux. (Contesté par M2 et M3, neutre pour M4 et M5.)
- Variante M3-L03 (contestée) : « la surface reste identique (§8.0 bis #3) ; seul le point où la géométrie « avant » est capturée varie. … HTML pur et îles : `udixio.motion.set(el, attrs)`, qui mesure puis écrit. » Familles : F7, F8. Nature : instance.
- Avantages : une seule forçage de layout au lieu d'un par élément ; First est pris avant la mutation par construction ; même primitive pour HTML, Astro et les trois frameworks. [M2] une passe de lecture et d'écriture pour tous les environnements. [M3] primitive unique « avant / après / inversion » en une passe de lecture. [M4] forme TS `motion.layout(portée, mutation)` pour les mutations impératives, First lu avant mutation par construction. [M5] le point d'écriture unique est le bon endroit pour la mesure « avant » / « après » / « jeu ».
- Limites : seuls les changements passés par la transaction sont capturés ; la mutation doit être synchrone ; un changement asynchrone (donnée reçue, redimensionnement) n'est pas couvert sans L02. [M2] mutation synchrone requise ; changement asynchrone non couvert sans M1-L02. [M3] mutation synchrone obligatoire ; changement asynchrone non couvert. [M4] mutation synchrone exigée, changements asynchrones non couverts. [M5] trois points d'écriture pré-mutation coexistent (M1-L01, M3-L03, M5-L01).
- Conflits : M1-04 (frame unique) ; M1-L02, M1-L04, M2-L01, M3-L02, M3-L03, M5-L01 (union des annotations et du choix).
- Cohérence : réutilise le verbe `layout` (R12), la frame unique (§8.0 M1-04) et le handle commun. Nouveauté : `motion.layout(portée, mutation)` est la forme TS de `data-motion="layout"` pour les mutations impératives (HTML pur, Astro). Justifié car une mutation de DOM n'a pas d'attribut à lire ; les adaptateurs l'exposent sous la même surface (§8.0 bis #3) · jugements : ok 1 (M5) · exception 3 (M2, M3, M4)
- Verdicts : valide 3 (M2, M4, M5) · neutre 1 (M3) · conteste 0

### M5-L02 — Lint : variantes non observables refusées sur `layout` [fusionne : M4-L02, M2-L02 (lint et pont de diagnostic), variante M3-L04]
- Énoncé : un nœud dont la définition porte `layout` et qui utilise `hover:`, `focus:` ou `group-hover:` (ou une transition CSS écrite à la main) est une erreur de build qui cite la forme correcte : `emphasize` pour un état de survol (L03). Sur `layout`, seul un changement d'état écrit compte. Environnements : HTML et composants Udixio par lint de build ; noyau par erreur dev quand la règle est détectable à l'exécution.
- Familles : F2, F7, F22, F23
- Nature : global
- Variante M4-L02 (détection) : « `layout` ne s'exécute que sur un attribut ou une classe observés (React : état rendu ; Angular : binding ; Svelte : état lu ; HTML : `MutationObserver` avec `attributeFilter`, donc après mutation, avec la géométrie de M4-L01). Les changements purement CSS (`:hover`, `:focus-visible`, `:has()`, requêtes de conteneur) ne sont pas du layout : le lint de build signale une utilité géométrique (`justify-*`, `order-*`, tailles) sous un variant de pseudo-classe pour un élément en `layout`, et l'auteur pose alors un `data-*` écrit par `pointerenter` / `focusin`. » Familles : F2, F7. Nature : les deux.
- Variante M3-L04 (mécanisme sans écouteur par défaut) : « un changement dû à `:hover`, `:focus` ou une media query n'est pas un layout Udixio : le runtime ne l'écoute pas et ne le joue pas. … La sonde par propriété `@property` (technique Bramus) est opt-in seulement. » Familles : F2, F7, F20. Nature : instance.
- Variante M2-L02 (pont de diagnostic) : « un `layout` ne se déclenche jamais sur un état purement CSS … erreur de lint au build et erreur dev citant le manifeste. … Pont optionnel, réservé au diagnostic : `@property` enregistrée + `transition-behavior: allow-discrete` (technique R4), sans polling. » Familles : F2, F7, F19. Nature : les deux.
- Avantages : l'erreur la plus probable (animer un survol en `layout`) devient visible ; le message renvoie à la recette (L10). [M1] l'erreur la plus probable devient visible. [M2] une erreur de build pour `hover:` sur `layout`, contrat net avec Tailwind. [M3] l'erreur la plus probable (survol animé en `layout`) devient visible, avec recette. [M4] lint de build qui signale `justify-*` sous `hover:`, erreur au build (C5). [M5] une erreur de build sur une combinaison verbe / déclencheur est exactement la garde M5-S10.
- Limites : le lint ne voit pas les classes construites dynamiquement (déjà M5-S04) ; un `:hover` dans une feuille CSS écrite à la main demande un parseur CSS ; faux positif si le `hover:` ne change pas l'élément mesuré. [M1] classes dynamiques et CSS écrit à la main non couverts. [M2] pont `@property` fragile (bugs R4). [M3] lint aveugle aux classes dynamiques ; faux positif si le `hover:` ne change pas la cible. [M4] lint sur classes Tailwind heuristique. [M5] le pont `@property` + `allow-discrete` est fragile (R4), ne pas le proposer comme chemin par défaut.
- Conflits : M5-S04 (classes dynamiques refusées), M5-S10 (garde-fous), M5-V07 (erreur au build) ; union : M1-L03, M2-L02, M3-L04, M4-L02.
- Cohérence : garde-fous de M5-S10, format d'erreur de M5-V10. Nouveauté : règle croisée verbe × variante, justifiée par la limite `:hover` de §4.3. Exception déclarée : `emphasize` accepte `hover:`. · jugements : ok 3 (M1, M3, M4) · exception 1 (M2 : règle croisée verbe × variante, déclarée)
- Verdicts : valide 4 (M1, M2, M3, M4) · neutre 0 · conteste 0

### M5-L03 — Changement d'état non géométrique : `emphasize` avec `interrupt="carry"` [fusionne : M3-L06, M4-L03, M2-L03 (variantes)]
- Énoncé : rotation, couleur, échelle ou propriété personnalisée qui change avec l'état : verbe `emphasize`, aucun verbe nouveau. Définition : `defineMotion('chevron', { verb: 'emphasize', spring: 'soft', interrupt: 'carry' })`. HTML : `<svg data-motion="chevron" class="data-[open]:rotate-180">` ; React : `useMotion(chevron, { state: open })` ; Angular : `<svg udxMotion="chevron" [udxMotionState]="open()">` ; Svelte : `{@attach motion(chevron, { state: open })}` ; noyau : `motion(el, chevron, { state })`. L'attribut `data-motion-interrupt` peut réécrire la valeur par élément.
- Familles : F2, F13
- Nature : instance
- Variante M3-L06 (`trigger="state"`, reprise estimée) : « rotation, couleur, échelle ou propriété personnalisée qui change avec un attribut d'état (L01) se déclare avec `emphasize` et `trigger="state"` (trigger déjà listé en §4.1). La reprise est `carry` par défaut : la vitesse de départ est estimée sur deux valeurs calculées lues en frame (`velocity.source: estimated`), ou exacte quand le moteur la fournit. Le ressort passe par anime.js ; en natif, une courbe `linear()` pré-calculée suffit quand la spec n'exige pas de reprise. » Familles : F2, F13, F1. Nature : les deux.
- Variante M4-L03 (ressort en jeton) : « rotation, couleur, échelle ou propriété personnalisée qui change avec un état s'écrit `data-motion="emphasize"` avec `data-motion-trigger="state"` ; … Le ressort est un jeton `easing="spring-<nom>"` (springs M3, F1). La reprise est `carry` par défaut (§8.0 bis #4) : si la cible n'est pas compositable ou si WAAPI n'expose pas la vitesse, le JS prend le relais. » Familles : F1, F2, F13, F14. Nature : instance.
- Variante M2-L03 (`@property` comme unité d'animation) : « rotation, couleur, échelle ou autre propriété liée à un état passe par `emphasize`, déclenché par changement de `data-state` ou d'attribut `data-motion`. La valeur animée est une propriété enregistrée (`@property --udx-rotate`, `--udx-scale`) : le provider anime la variable … Reprise `carry` par défaut pour ce verbe (§8.0 bis #4). » Familles : F1, F2, F13, F15. Nature : instance.
- Avantages : aucune grammaire nouvelle ; la reprise avec vitesse est un choix écrit, pas un défaut caché ; même forme pour rotation et couleur. [M1] `emphasize` avec reprise écrite, même forme pour rotation et couleur. [M2] aucun verbe nouveau ; reprise par vitesse écrite dans la définition, pas un défaut caché ; `@property` comme unité d'animation. [M3] aucune grammaire nouvelle ; reprise écrite, pas cachée. [M4] `interrupt="carry"` explicite, `emphasize` pour rotation et couleur.
- Limites : `carry` force le backend JS sur les propriétés non numériques (M5-S08) ; une couleur n'a pas de vitesse numérique simple ; `emphasize` est `restart` par défaut, donc exception à déclarer. [M1] `emphasize` déclaré `restart` par défaut ici, `carry` chez M2-L03, M3-L06, M4-L03 : désaccord de défaut ; option `interrupt` absente de la liste des options partagées. [M2] toute valeur animée doit être déclarée avec `@property`. [M3] `emphasize` est `restart` par défaut (R12), donc `carry` écrit à la main ; couleur sans vitesse numérique. [M4] défaut `restart` pour `emphasize` contredit §8.0 bis #4 (exemple : `carry` pour un changement d'état) ; `spring: 'soft'` en chaîne diverge du jeton.

### M5-L04 — Panneau monté : le preset `collapse` devient `layout` [fusionne : M2-L04, M1-L06, M3-L07 (variantes) ; écarté : M4-L04]
- Énoncé : accordéon, disclosure, hauteur `auto` : le panneau reste dans le DOM et sa hauteur est un `layout`. Le preset `collapse` passe de `appear` / `disappear` à `layout`. L'état reste celui du composant (`hidden`, `open` ou `data-state`) ; le preset pose `inert` tant que le panneau est fermé. HTML : `<section data-motion="collapse" data-state="closed">` ; React : `useMotion('collapse', { state: open })` ; Angular : `<section udxMotion="collapse" [udxMotionState]="open()">` ; Svelte : `{@attach motion('collapse', { state: open })}` ; noyau : `motion(el, 'collapse', { state })`.
- Familles : F2, F3, F7
- Nature : instance
- Variante M1-L06 (mécanique CSS, `grid-template-rows` 0fr → 1fr) : « un panneau reste dans le DOM et se referme par transition de `grid-template-rows` (0fr → 1fr) sur un parent `display:grid`, sans JS ; `interpolate-size` (Chromium) n'est qu'une amélioration ; le repli JS mesure `scrollHeight` et anime `height` en px ; `display:none` n'est jamais posé pendant une animation … la fermeture finale passe par `inert` et `hidden="until-found"` (à vérifier par moteur). » Familles : F2, F3, F7, F20. Nature : global pour le CSS, instance pour le repli JS. (Contesté par M4 et M5 : « pas de verbe » hors grammaire, repli `restart`.)
- Variante M2-L04 (`inert` immédiat, hauteur native puis FLIP) : « accordéon ou disclosure ne passe pas par la présence (F3), le nœud reste dans le DOM. ## 3. Faits framework tranchés par M4

Repris tels quels de `M4-annotations.md` (section « Faits framework tranchés »).

- Angular : `afterRender` (EarlyRead compris) s'exécute après la détection de changements, donc après la mise à jour DOM du template : ce n'est pas un point pré-mutation. Le vrai point est le gestionnaire d'événement, lu avant l'écriture du signal (appliquée seulement à la détection suivante). `effect()` et `ngDoCheck` : non tranché, ne rien fonder dessus sans spike.
- Svelte : `$effect.pre` s'exécute avant la mise à jour du DOM du composant qui le déclare. Il ne voit pas un changement porté par un autre composant. Confirmé.
- React : une fonction n'a aucun point pré-mutation ; `useLayoutEffect` s'exécute après mutation. `getSnapshotBeforeUpdate` d'un wrapper de classe est un vrai point pré-mutation, seulement si le wrapper se re-rend dans ce commit (passer l'état en prop).
- React 19.3 : `<ViewTransition>` annoncé stable (react.dev, 2026-09-09). `addTransitionType` : non tranché, la page de référence dit encore Canary.
- Svelte 5 : transitions locales par défaut (`|global` pour l'inverse) : probable, à tester.
