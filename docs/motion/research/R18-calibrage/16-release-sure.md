# Proposition : chaîne de release sûre et contenu réellement testé

**Statut : conception à revoir avant implémentation.** Aucun workflow n'est modifié ici, aucune publication externe n'est exécutée. Cette proposition complète la tranche release de [15-ci-plan.md](15-ci-plan.md) ; elle ne prétend pas que les protections décrites existent déjà.

## Constat et menace

`release.yml` accepte un `workflow_dispatch` sur une référence choisie, crée immédiatement un jeton GitHub App, installe et exécute le code de cette référence avec des permissions d'écriture ; le chemin beta/next reçoit aussi `NPM_TOKEN`, crée le commit et les tags puis publie dans le même processus. Le `git push --atomic` protège d'une branche déplacée au push, mais ne prouve pas que le commit versionné publié a passé les tests. Le chemin stable teste avant versionnement, pousse commit et tags puis ouvre une PR. `publish.yml` accepte toute PR fusionnée vers main dont le nom de tête commence par `release/v`, y compris une tête de fork, et checkout la tête **courante** de main : une autre fusion entre l'événement et le checkout peut changer le contenu publié. Il dispose de `contents: write`, de `NPM_TOKEN`, ne réinstalle pas explicitement les dépendances, et fusionne ensuite la tête courante de main vers develop. Il utilise Node 22 contre 24 dans `release.yml`.

Un contributeur de fork peut choisir `release/v…` et proposer du code, scripts d'installation ou de build malveillants. Le nom de branche, un manifeste ou un artefact fourni par cette PR ne constituent pas une autorisation. Un acteur pouvant modifier la branche source ou déplacer un tag pendant l'exécution peut aussi substituer le contenu. Un paquet ou une dépendance compromis peut tenter de voler les secrets ou d'altérer les artefacts. Les protections GitHub, les approbateurs et le registre sont dans la frontière de confiance ; une compromission de ces administrateurs ou de code déjà approuvé reste un risque.

## Choix proposé

Deux approches ont été considérées : publier directement depuis le job qui versionne (simple mais concentre les secrets et ne contrôle pas le commit final), ou préparer un commit, tester ce commit puis publier des archives figées dans un job protégé. Retenir la seconde. Une troisième option, reconstruire dans le job de publication, donnerait accès à ses identifiants aux scripts du dépôt et aux dépendances ; elle est écartée. Les décisions ci-dessous sont proposées pour revue, pas une description du comportement actuel.

1. **Préparation autorisée.** Exécuter le contrôleur `workflow_dispatch` depuis une référence protégée et immuable, dont le workflow et les scripts de contrôle sont revus ; refuser toute exécution chargée depuis une référence candidate. Le SHA candidat est une donnée fournie au contrôleur, jamais l’origine de son code de décision. Restreindre les candidats à une branche source explicitement autorisée et protégée (par exemple `develop`), vérifier le dépôt, la référence et le SHA exact côté contrôleur ; ne jamais interpoler une entrée dans une commande shell. Le job de préparation calcule les versions Nx indépendantes à partir du SHA d'entrée immuable, sans publication. Le code qui calcule le plan ne reçoit ni secret npm ni OIDC ; aucun jeton d'écriture n'est disponible pendant installation, tests ou build. Une étape/job distinct, sur runner vierge, contrôle indépendamment le diff proposé avant d’utiliser une GitHub App à droits minimaux pour créer le commit/branche de release par comparaison de SHA attendus. La politique contrôle les chemins et changements autorisés, les versions et le lockfile ; toute modification de scripts ou configuration exécutable exige une revue explicite et ne peut pas être autorisée par le manifeste candidat lui-même. La création du commit ne constitue pas une approbation de publication : celle-ci intervient séparément avant publication. Il ne lance pas de scripts du dépôt avec ce jeton. Échec fermé si la source a avancé ; recommencer depuis sa nouvelle tête. Protéger les branches et tags, interdire les force-push et limiter la création de branches de release à l'App. Ne pas faire confiance à une simple convention de nom.
2. **Stable.** Ouvrir une PR interne de la branche de release vers `main`. Exiger revue et contrôles de branche, et l'identité du dépôt source, de la branche et de l'App autorisée. Le contrôleur ne déclenche la suite que pour une PR fusionnée vers `main`, liée à une préparation autorisée par un identifiant immuable et au SHA de tête approuvé. Vérifier l'événement et les données GitHub, pas seulement le nom ou une étiquette éditable. Récupérer le SHA de tête effectivement approuvé et comparer son arbre à celui du commit de merge sur main ; la fusion doit conserver exactement le contenu versionné approuvé. En cas de dérive, de changement de tête après approbation ou de divergence d’arbre, arrêter et soumettre le nouveau contenu à revue et validation ; ne pas déduire cette relation du nom de branche. Le SHA publié est **`pull_request.merge_commit_sha`**, vérifié présent et ancêtre de `main`, jamais `main` résolu au moment du checkout. Une fusion ultérieure de main ne change pas ce SHA. Vérifier explicitement les particularités du mode de fusion autorisé (merge, squash ou rebase) ; tant que leur contrat n'est pas démontré, n'autoriser qu'un mode et refuser les autres.
3. **Beta/next.** Créer un commit de version immuable par la même procédure contrôlée, puis le pousser avec comparaison atomique à la tête source attendue. Le SHA effectivement créé et poussé est le SHA candidat, pas le SHA de départ du dispatch. Refuser toute référence non autorisée, toute modification non attendue du plan de version et tout déplacement concurrent. Les tags Git doivent pointer sur ce commit ; la publication n'a lieu qu'après validation de ce SHA. `beta` et `next` restent des dist-tags npm distincts et ne passent pas par une PR vers `main`.
4. **Validation et construction sur runner jetable.** Checkout par SHA exact avec `fetch-depth: 0`, `persist-credentials: false` et `contents: read` ; vérifier `git rev-parse HEAD` et l'arbre attendus. Installer Node/pnpm épinglés de manière identique pour les trois canaux et installer les dépendances avec lockfile gelé. Sans secrets, sans OIDC ni jeton d'écriture, exécuter les tests et builds de release des paquets avec `--skip-nx-cache`, puis la garde motion : installation locale des trois navigateurs Playwright et `MOTION_BROWSERS=chromium,firefox,webkit` avec `--skip-nx-cache` sur la cible de test appropriée. Tout échec bloque. Construire et empaqueter chaque paquet sélectionné depuis ce même checkout ; vérifier les métadonnées des archives et leur contenu, y compris les dépendances internes et licences. Le build doit être exécuté après le versionnement et ne pas modifier les sources versionnées attendues ; contrôler l'état Git. Le job produit un manifeste de noms, versions, chemins et empreintes SHA-256 des archives et le SHA Git. Le contrôleur lie explicitement ce manifeste à l’identifiant d’artefact, au run, à sa tentative, au digest d’artefact et au SHA candidat ; toute discordance bloque. Aucun cache ou artefact exécutable issu d'une PR ou d'une autre exécution n'est utilisé.
5. **Publication isolée et protégée.** Un job sur runner vierge dépend de la réussite de la validation du même run et SHA, utilise un environnement GitHub protégé avec approbateurs et restrictions de branches, et reçoit l'identifiant npm ou `id-token: write` seulement après cette validation et cette approbation. Privilégier npm trusted publishing/OIDC si la configuration réelle de chaque paquet et du workflow le permet ; sinon secret npm limité, stocké dans cet environnement et non au niveau du dépôt. Vérifier auprès de npm les contraintes de provenance et de trusted publishing avant migration. Épingler les actions à des SHA complets vérifiés et les outils à des versions déterminées. Télécharger uniquement l’artefact identifié pour ce run et cette tentative ; vérifier son ID, digest, manifeste, hashes et métadonnées contre le plan autorisé et le SHA validé. Traiter les archives comme des données non fiables : interdire chemins absolus ou traversées (`..`), liens dangereux et extraction hors répertoire isolé ; préférer l’inspection sans extraction et refuser toute entrée ambiguë. Ne pas exécuter de script ni de code provenant de l'archive ou du dépôt avec les secrets ; publier les tarballs explicites avec scripts npm désactivés, et vérifier ce comportement dans l'implémentation. Le manifeste seul ne prouve pas l'honnêteté du build : la confiance vient du commit approuvé, de l'isolation du runner et de la liaison au run. Ne pas injecter le secret dans des arguments ou des logs.
6. **Tags et retour develop.** Différer la création des tags Git stables jusqu'au commit de merge effectivement testé ; ils doivent pointer sur ce SHA, et leur nom/version correspondre au manifeste de release. Contrôler absence ou identité exacte des tags existants, puis création atomique et protection contre déplacement. Pour les prereleases, vérifier de même la correspondance tags/commit testé. Le retour vers develop est une opération distincte, après publication réussie, ciblant le SHA stable exact et non la tête courante de main ; employer une PR soumise aux protections et arrêter sur conflit. Aucun échec de retour ne doit déclencher une nouvelle publication aveugle.

## Contrat Nx et reprise

`nx.json` utilise `projectsRelationship: independent`, deux racines de projets et des changements conventionnels ; les versions peuvent différer entre paquets. Ne pas déduire la release de la seule version de `ui-react`, ni publier tous les projets à partir d'un tag global. Conserver explicitement la sélection Nx et les données de version calculées, leur graphe de dépendances et la liste exacte des archives dans le plan ; vérifier chaque nom/version contre le commit candidat et les archives. Adapter `scripts/release-prerelease.mjs`, qui conserve aujourd'hui `releaseGraph` et `projectsVersionData` en mémoire puis pousse et publie, pour séparer préparation et publication sans perdre cette sélection. Définir et tester un format de plan versionné, validé et non exécutable, ainsi que la résolution des dépendances internes et des tags Nx par paquet. En l'absence de changement, arrêter sans publication ni création de release vide. Sérialiser stable, beta et next avec un verrou durable commun couvrant préparation, attente de PR et publication. La concurrence GitHub Actions ne garantit ni FIFO ni verrou durable pendant la vie d’une PR : elle ne suffit pas seule. Le verrou doit avoir un propriétaire et une expiration ou procédure de libération auditée, empêcher les validations concurrentes et être repris explicitement après incident. À la reprise après attente, revalider la tête source, le plan, les versions et tags au registre ; si le contexte a changé, invalider le plan et recommencer. Si ce verrou ne peut pas être garanti, n’autoriser qu’une release active par contrôle externe vérifié avant chaque étape, et bloquer en cas d’incertitude.

Une publication multi-paquets n'est pas atomique. Avant toute reprise, comparer chaque nom/version et son intégrité au registre : ignorer seulement les paquets déjà publiés avec l’intégrité attendue, publier les manquants depuis les mêmes tarballs validés et conservés, arrêter sur divergence ou dist-tag inattendu. Vérifier et réconcilier séparément chaque dist-tag après publication complète, sans supposer que les versions déjà publiées puissent être annulées ou remplacées. Ne jamais republier une version existante différente ni recalculer silencieusement le plan. Documenter le run, les checksums, tags et résultats individuels. En cas d'incident, bloquer les nouvelles releases, révoquer les identifiants compromis, déplacer les dist-tags vers des versions connues saines après examen et corriger par une nouvelle version ; un unpublish éventuel dépend des règles npm et ne constitue pas un rollback garanti. Garder commit, tags et preuves pour diagnostic ; ne pas réécrire l'historique publié.

## Vérification sans publication externe

- Tests de politique sur événements synthétiques : PR interne valide, PR de fork `release/v…`, branche ou dépôt incorrect, auteur/identifiant de préparation inconnu, PR fermée sans merge, SHA absent, branche déplacée et tentative de tag déplacé ; tous les cas non autorisés échouent avant accès aux secrets.
- Simuler les trois modes de fusion et une seconde fusion sur main après l'événement ; confirmer que le checkout, les tests, les tags et le manifeste désignent le SHA de merge prévu. Simuler des modifications dues au merge et les refuser selon le contrat choisi.
- Pour stable, beta et next, créer des commits de version dans un dépôt Git temporaire et utiliser un registre local isolé ou une simulation de publication ; vérifier sélection Nx multi-paquets, versions indépendantes, dépendances internes, tags, dist-tags, absence de changements et conflit de push atomique. Bloquer tout accès au registre public pendant ces essais.
- Forcer l'échec de chacun des trois navigateurs, d'un build, d'un hash et d'une approbation : aucun accès aux identifiants de publication ni publication ne doit suivre ; les droits nécessaires à la création antérieure du commit sont évalués séparément. Vérifier que secrets et OIDC sont indisponibles dans les jobs de préparation non fiables et de build, y compris sur fork. Tester une publication partielle et la reprise idempotente avec le registre local.
- Exécuter `actionlint` et les tests du contrat, puis observer des runs GitHub réels sans publication, y compris les protections d'environnement et les permissions effectives. Ne déclarer la garde en place qu'après preuve des SHA, des trois moteurs et de l'absence de chemin de contournement.

## Points à résoudre avant activation

La disponibilité et les droits effectifs des environnements, règles de branches/tags, App et trusted publishing doivent être vérifiés dans les paramètres GitHub et npm ; ce dépôt ne démontre pas leur configuration. La validation exacte de l'identité de préparation, le protocole Nx exact de build, versionnement, graphe et sélection selon `nx.json`, les commandes de sérialisation/reprise, le packaging par projet et les règles d'artefact doivent être prototypés et revus avant modification des workflows. Les scripts d'installation restent exécutables dans le job non privilégié ; il faut aussi limiter son accès réseau et sa persistance selon les capacités du runner. Les navigateurs récents Playwright ne prouvent pas C13 sur Firefox ESR et Safari réels : fournisseur, versions minimales et exécution attestée restent à définir séparément. Une revue du présent document précède toute modification des workflows et toute activation de la publication.
