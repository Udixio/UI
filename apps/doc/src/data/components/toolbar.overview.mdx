## Usage

Toolbar groups related actions in a docked or floating container. It is a
composition wrapper: put `Button`, `IconButton`, an image, or another
appropriately labelled custom control inside it. The toolbar does not duplicate the action's state,
tooltip, or keyboard behavior.

## Docked toolbar

Use a docked toolbar at the bottom of the current app surface. It can be paired
with a FAB when the FAB represents the primary action; the screen owns the
placement and the action state.

## Overflow actions

Pass an `actions` model when the toolbar should manage visibility for you.
`maxVisible` keeps the first actions visible and moves the rest into a generated
menu; set `pinned: true` on an action that must remain visible. The example uses
several editing actions so the generated menu has meaningful content.

The generated menu uses automatic placement by default: it opens below a
horizontal toolbar in the upper half of the viewport and above it in the lower
half; vertical toolbars use the equivalent right/left rule. Use `morePosition`
to force a specific placement when needed.

## Guidelines

- Toolbars are 64dp high by default; use `IconButton size="small"` for the
  48dp toolbar slots and keep every interactive child at or above that target.
- Docked toolbars use 16dp edge padding and 8dp minimum spacing between actions;
  compact widths distribute the actions evenly.
- Floating toolbars use compact 8dp internal padding and 4dp between actions.
- Keep a horizontal floating toolbar at least 16dp from surrounding edges and a
  vertical floating toolbar at least 24dp away.
- Docked toolbars belong at the bottom of the surface and should not be shown
  simultaneously with a navigation bar.
- Avoid multiple toolbars in compact layouts. Use overflow when actions do not
  fit and keep the overflow action in its logical position in RTL layouts.

## Accessibility

The root exposes `role="toolbar"`. Provide `accessibleLabel`, or connect an
external heading with `aria-labelledby`, so assistive technology can identify
the action group. In `actions` mode, the generated trigger exposes its menu
relationship and the menu items reuse each action's accessible label. In
composition mode, children own focus, activation, pressed state, and labels. In
particular, an `IconButton` should always receive a meaningful `label`.

This wrapper intentionally does not implement roving focus or arrow-key
navigation. If a product needs a composite keyboard model, use a dedicated
interaction pattern around the child controls rather than assuming that every
toolbar is a single composite widget.
